# 组织邮件网络

组织是由共享背景和独立智能体对话组成的邮件网络。成员可以按职责自由通信；布局只表示成员位置，不决定执行顺序。没有永久连线、入口流股、输入/输出逻辑门、批次门槛或排队/插入配置。本文描述当前工作树，不表示这些改动已随公开版本发布。

## 术语与历史记录

产品与模型统一使用「组织 / Organization」。普通成员注册六个邮件工具，管理员额外注册 `organization_edit`。模型自动收到的 World State 只使用 `organization.execution` 与 `organization.mailbox`；全员目录、部门树和其他成员的状态通过主动查询取得，不再自动注入 `organization.awareness`。新工具结果中的组织名为 `organizationName`。不为旧 `workflow_*` 工具记录增加兼容分支；本次开发环境中对应旧聊天按用户要求单独删除。当前内部消息来源 DTO 仍使用 `workflowName`，工具结果在出口映射为 `organizationName`；不批量替换用户填写的组织名称或背景。SQLite 表、内部 DTO、IPC 方法、Trace 标识和模块路径保留原标识，本次命名调整不改变存储 schema 或收发行为。

## 定义与编辑

开发期 `schemaVersion: 1` 定义含 `id`、`name`、`description`、`background`、`nodes`、`departments`、`viewport` 和版本字段。节点最多 128 个、部门最多 64 个，定义大小、目录容量及乐观并发限制仍由 Rust Core 校验。坐标必须有限，ID 必须唯一。

- `agent`：ID、名称、坐标、`modelConfigId`、`permissionMode`、`receives`、`task`、`delivers`。

每个智能体节点可保存职级 `rank`（1–99，数字越大越高，默认 1）、管理身份 `managementRole`（普通成员、组织管理员、部门管理员，默认普通成员）和直属部门 `departmentId`。职级与管理身份独立；职级高本身不赋予管理员身份。部门保存名称、矩形范围与 `parentId`，直属组织为 1 级，逐层嵌套形成下级部门。成员完整位于部门框内时归属最内层部门，祖先部门由树推导；部门外为直属组织。存储以明确的归属和父级字段为准，不让后端依赖前端节点卡片的像素尺寸。

不接受 `flows`、`boundaryPositions`、`nextFlowSequence`、门节点或消息接收策略。没有旧定义转换或缺省补门。无效记录仍按现有目录机制隔离，避免损坏条目阻断整个目录；不会自动重写旧数据。

设置中的「基本信息／组织设计」、名称/权限/模型顶部配置行和节点任务配置保持原有设计。节点侧面板新增「职级」页，仅配置职级与管理身份，不重复展示画布已有的部门归属。部门没有独立侧面板；选中部门后仅在顶部显示上级部门、可编辑名称和删除操作，名称前用建筑图标。接收说明始终可编辑，无需先连线；没有新增接收配置页。添加菜单只提供智能体和部门，画布拖入与粘贴也只创建智能体节点；选择部门后在画布拖出虚线框，完整嵌套形成上下级部门，拒绝部门框部分交叠。空画布没有合成用户入口。

部门可改名、移动和缩放；移动会带上内部成员与下级部门。删除框保留成员和下级部门，归属重新计算；部门管理员移出全部部门后恢复普通成员身份。一键优化布局按现有归属逐层整理：排开直属成员、整理下级部门，并自动调整部门框以容纳内容。直属组织的成员和一级部门一起排布；空部门同样保留。优化只改变位置和框尺寸，不改变部门层级、成员归属、职级、管理员身份及任务配置，完成后适应画布。重复点击结果稳定，一次撤销恢复优化前布局。可拖动、缩放、适应画布、删除、撤销/重做；Command/Ctrl+C/V 复制节点配置和职级，产生独立 ID，所属部门按粘贴位置重新计算。文字输入框保留原生复制粘贴。平移缩放不占内容撤销步骤。

组织实例在激活时保存独立的完整定义，之后模板编辑、删除与组织相互独立。模板标识只作为内部来源信息，运行时和已激活组织编辑不再从模板加载配置。已有组织可在线修改成员、部门、职责、职级、管理员身份和模型默认值；保存保留启停状态，不因有人运行而禁止整个组织编辑。保存使用组织 revision 防止覆盖并发变动；移除成员保留对话和历史。

模型及权限是节点的默认值。首次绑定和明确修改节点模型/权限时更新后续输入配置；仅修改职责、职级或布局不覆盖用户在对话中选择的配置。保存模板不创建对话；确认激活实例时才为未绑定智能体创建对话。可选所属项目只决定新建对话的位置，不限制跨项目绑定。

模板编辑与组织首页的操作异常复用应用统一提示弹窗，只显示与当前操作对应的说明和「知道了」，不展示后端异常、错误码或可展开的技术详情。关闭提示不丢弃编辑内容；加载重试、版本刷新和提交后同步恢复仍有独立入口。保存冲突仍保留草稿与另存副本路径，不绕过版本校验。严格字段检查失败不直接等同于用户填错配置。

## 状态所有权与工作区

模板、实例、绑定、邮件和工具幂等性由 Rust Core 持有；Renderer 只编辑草稿、展示状态及处理视口。组织实例没有单独的模型 Run，每个智能体仍是独立根对话。子 Agent 协作邮箱与本系统不同，不能互换授权或队列。

模板的 `enabled` 是当前校验是否通过；实例 `enabled` 表示用户是否开启；`running` 来自真实对话活动。三者不互相替代。保存、启停、删除和草稿保留 revision/CAS；模板使用情况及其版本守卫已移除；查询实例只读取独立实例目录。唯一绑定、开启颜色占用、归档保护、失效关闭和未保存编辑保护保留。

组织首页、组织编辑和看板统一位于右侧栏。已激活组织显示正常的编辑器与「保存修改」，不展示模板选择、模板名称或模板修订提示；新建时可从模板复制后继续编辑。组织编辑复用模板画布与任务/职级面板，同时保留指定已有对话与拖入对话的能力。左侧组织入口打开首页并最大化；已绑定对话的入口打开所属看板。双击节点在中央打开真实对话并恢复侧栏宽度。对话顶部菜单展示其他已绑定协作成员，不再区分上下游。切换聊天或标签保留画布状态。

## 邮件生命周期

每次发送为每位收件人创建独立、不可变的消息信封和一个持久输入收据，不再跨消息组批。信封保存稳定消息 ID、组织、发送/接收节点和当时绑定的对话名称、正文、时间及可选 `replyToMessageId`。模型不能自行填写发送者身份。

| 邮件状态     | 含义                                     |
| ------------ | ---------------------------------------- |
| `pending`    | 未领取，保留在收件箱中                   |
| `processing` | 已被当前轮次领取，等待正式投递或正在处理 |
| `processed`  | 模型显式完成，或持有它的轮次正常结束     |
| `stopped`    | 持有它的轮次被停止                       |
| `failed`     | 投递或处理轮次失败                       |
| `recalled`   | 发件人在尚未领取时撤回                   |

`processed` 表示本系统的处理结束，不证明业务结果正确。内部 input 的 pending/claimed/applied 等状态仅记录传输事实，不能直接充当前端邮件状态。历史失败邮件不阻塞后续邮件。已处理、已撤回的状态不会被后续轮次停止、失败或恢复覆盖。

### 唤醒与主动领取

1. 来信写入邮箱并通知调度器。运行中的节点不会自动插入其他来信。
2. 节点处于普通空闲状态时，调度器按到达顺序领取最早的一封，走现有根 Turn 准入并唤醒它。
3. 轮次中模型通过邮箱查询了解剩余来信，再用 `organization_accept` 主动领取任意待处理邮件。领取不新建 Run，正文在同轮下一次安全采样边界正式交付。
4. 轮次正常结束时，仍归属该轮次的 processing 邮件自动变为 processed；模型也可随时调用 `organization_complete` 完成已正式交付的指定邮件。
5. 回到空闲后仍有 pending 邮件，就再次按顺序取一封唤醒。没有未处理邮件时保持空闲。

用户点击停止会保留停止屏障，后续邮件留在邮箱，不立刻唤醒。用户手动发送新消息恢复该对话后继续正常机制。审批、等待用户交互、运行中或并发名额不足均不视为可自动唤醒的空闲。工具查询和 World State 更新不恢复停止状态。

组织只包含独立智能体成员；用户通过成员对话发起需求，不存在用户占位节点或手工确认输入的执行分支。

## 动态工具与在线编辑权限

所有工具仅在已准入、仍有效且开启组织的独立根 Run 中挂载。实例停用或当前成员资格失效后下一次采样移除；每次工具执行仍复验冻结的 Run 身份和当前成员资格。历史消息、checkpoint 或子 Agent 不能自行取得组织授权。

| 工具                       | 参数与作用                                                                                                                                                |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `organization_send`        | `{ messages: [{ to, message }] }` 按成员名发信；回复用 `{ replyTo, message }`，由原信确定收件人                                                           |
| `organization_get_state`   | 必填 `reason`；`view` 为 overview（默认）、structure、members、runtime、configuration。支持按成员姓名、职责关键字或部门查询，运行状态与配置另有过滤和分页 |
| `organization_get_mailbox` | 自己的 inbox/outbox；支持消息 ID、状态和游标过滤                                                                                                          |
| `organization_accept`      | `{ messageIds }`，将自己的 pending 邮件领取到当前轮次                                                                                                     |
| `organization_complete`    | `{ messageIds }`，将当前轮次已正式接收的邮件标记已处理                                                                                                    |
| `organization_recall`      | `{ messageIds }`，撤回自己发送且仍 pending 的邮件                                                                                                         |
| `organization_edit`        | 管理员专属：`{ reason, changes }`，一次原子提交 1–32 个成员或部门编辑动作                                                                                 |

组织编辑由 `organization.management` 独立能力控制。组织管理员可管理全组织职级严格低于自己的成员；部门管理员只可管理本部门及后代部门的低职级成员。调整前后的职级均须低于操作者，不允许修改自己；普通成员没有管理工具，高职级本身不赋权。每次提交在事务中重新读取操作者、目标、部门树、运行身份和组织 revision；过期调用不能凭旧快照越权。管理身份可以在授权范围内调整，部门管理员不能任命组织管理员；部门移动同样检查受到影响的成员，不能间接移动自己、同级或更高职级成员，或把管理权扩展到原范围之外。

`organization_edit` 只有 `reason` 与 `changes` 两个顶层字段，动作使用扁平参数：

| action              | 内容                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `add_member`        | 必填 `name`、`task`；可选 `receives`、`delivers`、`rank`、`managementRole`、`department`、`model`、`permissionMode` |
| `update_member`     | 必填成员名 `member`，以及至少一个需修改字段；`name` 表示新名称                                                      |
| `remove_member`     | 必填成员名 `member`，保留其独立对话与历史                                                                           |
| `add_department`    | 必填 `name`，可选上级部门完整路径 `parent`                                                                          |
| `update_department` | 必填部门完整路径 `department`，可改 `name` 与 `parent`                                                              |
| `remove_department` | 必填完整路径 `department`，仅允许空部门；先调走直属成员和下级部门                                                   |

成员名在整个组织内唯一，部门名在同一上级下唯一，均忽略首尾 Unicode 空白与大小写；部门名称不含 `/`，完整路径例如 `人事部/薪酬组`。名称按本次采样看到的目录精确解析，不作模糊匹配。内部继续用稳定 ID 做权限与持久化，模型不会看到节点、对话、运行、投递等内部标识。具体邮件仍保留唯一 `messageId`。

编辑未传字段保持原样，`department: null` 表示直属组织，`parent: null` 表示一级部门，接收说明和交付要求传空字符串表示清空。`model` 使用 configuration 查询中可用模型的可读唯一名称。头像由后端分配；工具不接受头像、坐标、对话绑定或内部版本字段。修改职责原地编辑，保持成员身份和邮箱。新建部门后，下一次调用使用更新目录中的部门路径，不引入临时引用表达式。前端回执保留可读字段前后值；模型结果只保留名称、变更字段与精简后的有效配置，省略长职责正文和旧值。

新增成员默认职级 1、普通成员，归属调用者所在部门，使用调用者本轮模型和实际权限对应的配置。权限上限来自可信 Host 的实际执行权限，使用各权限分量逐项比较，不仅比较 default/full/custom 名称。新建和编辑后的权限不能超过调用者；无法精确表示默认继承权限或选择了越权权限时明确拒绝，不静默降级。模型必须可用；模型和权限变更只调整后续对话输入配置，并遵守已有模型切换及上下文压缩锁。普通职责、职级和部门编辑不强制打断当前任务。

新成员加入组织所选项目，尚未收到邮件时不启动轮次。移除立即撤销组织成员资格并终结该身份的未完成邮件，但不删除聊天。调用以 run/tool call ID 保存幂等回执，多动作任一失败则全部回滚。提交发布 `members_changed` 事件；明确修改模型或权限还发布对应的持久配置事件；首次提交的实时通知附带 `preferenceUpdates`，前端立即同步目标字段并排在已有草稿写入之后保存，避免排队消息保存带回旧配置。该通知按组织修订去重，历史快照和回执重放不附带这些值；前端仍保留用户随后主动切换的选项和输入内容。新增或调入成员只安排该成员的位置，部门迁移保持子树相对位置；按需扩大祖先框并避让发生碰撞的同层块，保留其余已有布局。删除不重排或缩框；仅文字、职级或管理身份编辑保留布局。

不提供退回工具。模型需要补充材料时可用 `replyTo` 回复原信；`to` 与 `replyTo` 二选一，转交给其他成员时使用 `to`。成员资格允许通信，不产生新的文件、命令或其他工具权限。

邮箱查询返回 pending 邮件的真实正文，读取本身不领取，也不改变未来自动唤醒。工具结果明确提醒模型：仅查询过的邮件仍会投递；决定现在处理时必须主动领取。模型没有新成果、信息或必要交接时可以不发信，禁止为了维持网络活跃而重复发送占位邮件。

发送/领取/完成/撤回以 Run + tool call ID 做持久幂等。发送时按模型看到的目录解析成员，事务内复验收件人资格版本，已移除或改绑成员不会因旧名称被复用而误收新邮件。回复只能指向自己的来信，由可信信封确定原发送者。原始语义参数与回执原子保存；重试先恢复原回执，不重新按名称寻址，相同调用 ID 携带不同请求拒绝执行。领取与撤回竞争使用同一事务和权威状态，已经领取的邮件不能再撤回。

邮件及人员管理已提交的回执可在中断恢复时读取，即使成员随后离组或权限被撤销。读取必须匹配原对话、轮次、工具调用和操作内容，只返回原结果；任何新操作仍需通过当前成员资格及权限校验，不会因恢复回执而重复发送邮件或创建成员。

主动领取的工具记录保留正文供 UI 展示，但模型结果及历史工具结果投影去除重复正文；正式内容通过单独 `WorkflowDelivery` 进入上下文，避免领取回执和正式投递双份注入。邮件是协作资料，不能冒充用户指令或授权。聊天气泡是 Host 投递记录的展示投影，不能再次作为普通 HumanText 重放；分叉保留来源展示，不继承原组织成员资格。

启动轮次的邮件仍展示在助手轮次前；轮内接手的邮件使用独立 `workflow_delivery` 时间线项，在其正式投递的 trace sequence 位置展示。实时事件只在投递记录持久化后发出，历史加载从相同记录和可信邮箱来源重建，不按来信时间猜测位置。折叠工具过程时仍保留轮内来信和前后回复；原始正文默认可见，辅助上下文按需展开。界面隐藏已被轮内时间线覆盖的独立气泡副本，但保留原始记录；刷新、全量保存及分支对话不得丢失来源或重新显示副本，缺少正式投递证据的邮件保持原有展示。

## World State 与 harness

每次采样准备时，模型自动更新的组织信息限定为自身：

- `organization.execution`：组织名称、公共背景，以及本人的姓名、完整部门路径、职级、管理身份、接收说明、任务、交付要求和可管理范围。不包含其他成员或完整部门树。组织 revision 与成员 incarnation 分开；其他成员或部门变化不会使当前成员轮次失效，自己被移除或改绑后旧轮次永远不能恢复该资格。
- `organization.mailbox`：本人的待处理/处理中数量，以及自上次模型实际观察以来的新邮件简短提示。新信提示使用累计到达数与序号，而非 pending 数差计算。

模板 ID、模板版本、内部执行版本和组织修订号仅留在 Host 状态中，不进入模型可见的 World State。组织修订号仍用于保存时的并发校验；仅布局、颜色、同事资料或这些内部字段变化不产生自动组织 diff。本人职责、所属部门路径、管理范围、组织名称/背景或自己邮箱发生变化时才更新对应分区。新快照与既有记录的模型重放遵守相同过滤规则：旧全员摘要、完整部门树及其历史增量不会重新进入模型上下文。解析部门路径和校验管理权限仍使用 Host 的完整目录，不能因模型看到的内容缩小而漏掉祖先部门或放宽授权。

提示复用已有 World State observed request 提交：预览、失败请求和只准备未发送的请求不消费新信通知；请求成功观察才确认该次截点。到达后又被领取/撤回的邮件不会因 pending 总数相同而漏报。刷新摘要不单独启动模型，也不把全部邮箱正文推入上下文。

`organization_get_state` 每次按调用理由返回明确的查询结果，不重复组织公共背景，也不再以 World State 已看过为由省略当前事实。工具分为五个视图：

| 视图            | 返回内容与使用方式                                                                                                                                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `overview`      | 默认只给成员数、部门数、各状态数量、邮件积压和有限的需关注事项；不附完整成员目录、长职责或邮件明细。                                                                                                                         |
| `structure`     | 按需查询部门层级和完整路径，可限定部门及是否包含子部门。                                                                                                                                                                     |
| `members`       | 成员目录；`search` 按姓名或职责关键字匹配，`department` 使用完整部门路径，默认包含下级部门。`member` 按姓名精确查询完整职责。目录预览被截断时明确标记。                                                                      |
| `runtime`       | 当前活动、等待审批/交互、待处理及处理中数量、最近轮次结果；支持 `status`、成员和部门过滤。默认不附邮件列表，精确指定 `member` 并开启 `includeMail` 才返回该成员待处理/处理中邮件的状态摘要。邮件正文仍由自己的邮箱工具读取。 |
| `configuration` | 仅管理员可查自己及有权管理成员的默认配置、当前草稿对应的下一轮配置，以及可执行模型的可读名称。                                                                                                                               |

列表分页默认 20 条、最多 50 条。后续查询使用返回的 `page.nextCursor` 并保持相同视图及过滤条件；每页都是新查询的快照，不承诺跨页冻结组织状态。结果明确标记总数、已返回数量、后续游标、空结果和截断情况。单人成员邮件摘要使用独立 `mailPage.nextCursor`/`mailCursor`，不因外层成员分页而丢失后续邮件。Host 先补齐候选成员的真实状态，再进行状态过滤、运行分页和概览统计，避免先截断成员后遗漏真正等待审批的人。

运行状态不从上一次失败推断当前失败，也不把旧 `in_progress` 或处理中邮件数量当作当前有模型运行的证据。没有可用绑定时返回 `unknown` 和 `bindingAvailable: false`；有持久轮次占用但缺少实际活动证据时也明确为 `unknown`。`waitingForApproval` 和 `waitingForInteraction` 始终是布尔值，其中交互等待只表示同步阻塞；异步问题未回答用 `hasPendingInteraction` 标记，模型仍运行时保持 `running`。

手动排队的轮次保留各自提交时的配置；已运行轮次的配置已冻结，不以草稿冒充正在使用的模型或权限。调用者本轮的模型和权限上限由 Host 单独给出，不跟随草稿变化；内部 Run/成员/对话标识不进入模型结果。模型目录不包含密钥，也不注入自动 World State。邮箱可按消息 ID 取正文；分页和正文预算必须明确标记，不能静默截断后推进游标而丢信。收发邮箱严格限定当前成员的收件人/发件人身份。

终态邮件结算挂在 `conversation_trace_repository::commit_trace_with_loaded_prefix`，与权威 Turn trace 同事务提交，包括正常结束、停止、人工交互终止和启动恢复。没有正式投递证明的已领取邮件不能被正常结束误标成已处理。持久输入、run/delivery 绑定和 trace 共同提供恢复去重。

调度器独立于前端：合并通知、按 sequence 分页推进可投递会话，配置/容量/权限暂不可执行时使用既有退避机制。模型配置变化、名额释放和新邮件会触发重新检查。每次仍走权威准入；没有自动 injection 通道，当前 Run 的额外 WorkflowDelivery 只能来自已领取邮件。

SQLite v65 为组织实例持久保存独立定义、为绑定保存独立成员 incarnation，并增加人事工具回执表；精确 v64 升级只复制当前组织配置并解除模板外键依赖，不改写旧 Run 的授权身份。v64 新增独立 `workflow_mail_*` 表，保存信封、输入、发送/操作回执、事件、Run 身份、来源和停止屏障。安装只增加空表及索引，不转换旧工作流数据，不重置项目或聊天。定义 schema 与存储 schema 独立。

## 前端与实时看板

模板、组织编辑和看板均没有永久边或逻辑门。模板与组织编辑节点在头像左侧显示职级数字：普通成员为圆圈，组织管理员和部门管理员为勋章轮廓；这不是邮箱按钮。实时看板展示当前部门边框，继续使用邮箱图标和未处理数量，头像在其右侧；节点悬停仍只显示原有角色、模型、权限和任务信息。

看板只根据真实 `sent`/`recalled` 事件短暂画连接，流水灯按事件中源/目标方向移动后消失。撤回事件由后端反向给出端点。领取/完成是本地操作，不伪造跨节点传输。事件按实例序号去重，首次打开、重新打开和隐藏期间不重播历史；减少动态效果时不播放流水动画。动态线不写入定义，不影响撤销或布局。

单击节点打开可收起的详情，显示待处理、处理中和历史邮件；双击仍打开对话。正文按节点分页读取，运行快照只传无正文的元数据。显示六种邮件状态，不用 runStatus 再猜测或覆盖邮件完成结果。

工具展示延续现有折叠状态栏：

- 状态查询不可展开，显示「已查看组织 · 调用理由」。
- 收件箱/发件箱有明确「组织」前缀，共用邮箱底座与向内/向外箭头；空结果不可展开。
- 领取、完成、撤回各有操作图标和状态文案，展开可见对应具体邮件、复制与对话跳转；部分失败不显示全成功。
- 发信展开显示发送正文与收件成员，名称来自 Host 信封，不从 UUID 或正文猜测。
- 组织编辑展示状态与调用理由，展开显示成员和部门变更及可读的字段前后值；模型和部门引用展示名称，不展示技术 ID。
- 不向用户显示 JSON、执行版本或技术详情，历史结果按当时回执呈现。
