# 组织：邮件与分层协作

组织（Organization）把多个独立根对话组成可持续协作的智能体团队。成员共享组织背景，分别拥有职责、模型、权限和邮箱；通过内部邮件分派任务、追问、交接和回传结果。部门组织成员，职级与管理身份约束在线管理，三者不限制成员之间的通信。

本文描述当前开发代码，不表示官网安装包已经提供。旧图工作流已移除；当前组织没有永久连线、逻辑门、固定执行路线或用户入口节点。代码路径、SQLite 表、RPC 和 Trace 中仍有 `workflow_*` / `WorkflowDelivery`，它们是现有实现标识，不能据此恢复旧产品行为。

## 1. 领域对象与状态所有权

| 对象     | 当前含义与所有者                                                           |
| -------- | -------------------------------------------------------------------------- |
| 组织模板 | Rust Core 保存的可复用成员、部门、背景与默认配置；保存模板不创建对话       |
| 组织实例 | 激活时保存完整独立定义、成员绑定、颜色和启停状态；模板修改或删除不影响实例 |
| 成员     | 绑定一个独立根对话，具有稳定成员身份、职责、职级、管理身份和直属部门       |
| 部门     | 具有明确父部门的树结构；根部门直属组织，成员直属部门和祖先范围分别计算     |
| 邮件     | 本组织内一位发件人向一位收件人的不可变信封，以及独立持久输入与处理状态     |
| 成员 Run | 正常对话运行；组织本身没有另一个总控模型 Run                               |

模板、实例、成员身份、绑定、邮件和幂等回执由 Rust Core 持有。Core Server 负责运行准入、真实状态查询和邮件调度；Renderer 只管理草稿、视口和展示。子 Agent 的父子树、Mailbox 和 Wake 是另一套协作系统，不能与组织邮箱交换队列或授权。

模板 `enabled` 是当前定义校验结果；实例 `enabled` 是用户开关；运行活动来自真实对话。保存、开启、正在运行和邮件已处理不是同一个状态。

## 2. 创建组织与独立配置

设置中的组织模板编辑器提供「基本信息」和「组织设计」。成员保存名称、模型、权限、接收说明、任务与交付要求；「职级」页设置职级和管理身份。当前 definition schema v1 最多包含 128 个成员、64 个部门；大小、唯一标识、坐标、层级和版本由 Rust Core 校验。

用户从左侧「组织」进入右侧栏首页，选择「激活新组织」，从模板复制后继续配置：

1. 选择名称、颜色及可选的所属项目。
2. 为成员绑定已有独立对话，或保持未绑定，在确认激活时新建对话。
3. 激活后实例默认开启；没有邮件、也没有用户输入时，不启动模型。
4. 在成员对话中提出需求，成员按职责发邮件协作；普通最终回复不会自动寄给其他成员。

一个对话最多绑定一个组织中的一个成员。子 Agent 对话、已归档或不可用对话不能用于绑定。已有对话可以来自不同项目；所属项目只决定自动新建对话的位置，不迁移已有对话，也不扩大文件访问范围。

已激活实例使用自己的完整定义，编辑器显示「保存」，不再从来源模板取配置。实例可在线修改背景、成员、部门、职责、职级、管理身份与模型默认值；保存使用实例 revision/CAS，并保留原启停状态。模板编辑、删除或校验失效不触发实例停用、配置复核或模板使用关系确认。

模型与权限是成员默认值。首次绑定或明确修改这些字段时更新后续输入配置；只改职责、职级或布局，不覆盖用户在对话中另选的模型和权限。运行中 Turn 的配置已冻结，手动排队输入保留提交时配置。

停用组织阻止新的发送和投递，不取消已运行的 Turn。同一成员身份的待处理邮件保留；重新启用须通过实例定义、模型、完整绑定、对话状态和颜色检查。启用实例独占颜色且其对话不能归档。移除组织保留对话，当前实现拒绝移除被判定为运行中的实例。

## 3. 部门、职级与管理权限

### 部门树与画布

部门具有名称、父部门和矩形范围。画布中成员完整落在部门内时，归属最内层部门；框外成员直属组织。部门框须相互分离或完整嵌套，不能部分交叠；最终存储的是明确的 `departmentId` / `parentId`，后端不凭前端像素尺寸判断管理范围。

部门名称在同一父部门下唯一，不能包含 `/`；完整路径例如 `研发部/实现组`。成员名称在整个组织内唯一。两类名称都忽略首尾 Unicode 空白和大小写判重，不作模糊寻址。

移动部门带上内部成员和下级部门；删除画布部门框保留成员与下级部门并重新计算归属。部门管理员移到所有部门之外会恢复普通成员身份。自动优化只整理位置和框尺寸，不改变部门层级、成员归属、职级、管理身份或职责；一次撤销可恢复。成员复制产生新 ID，部门按粘贴位置重新计算。

### 职级与管理身份

职级为 1–99，数字越大越高，默认 1。管理身份独立于职级，默认普通成员。

| 身份       | 在线管理范围                                            |
| ---------- | ------------------------------------------------------- |
| 普通成员   | 没有 `organization_edit` 能力；高职级本身不授予管理权限 |
| 组织管理员 | 可管理全组织内职级严格低于自己的成员                    |
| 部门管理员 | 只可管理本部门及其后代部门内、职级严格低于自己的成员    |

共同约束：

- 不能修改自己；目标修改前和修改后的职级都必须低于操作者。
- 部门管理员不能任命组织管理员，不能把目标或部门移到原管理范围之外。
- 移动部门同时检查受影响成员，不能借移动子树间接修改自己、同级或更高职级成员。
- 创建或修改后的执行权限不能超过调用者本轮的实际有效权限。比较各权限分量，不只比较 default/full/custom 名称；不能精确表示或超限时拒绝，不静默降级。
- 管理身份只授予组织人员配置能力，不替代文件、命令、浏览器、MCP 或用户批准规则。

例如：组织管理员「协调员」职级 90；研发部管理员职级 60，部门下成员职级 10；审阅部另有管理员与成员。研发部管理员可以调整自己部门低职级成员及下级部门，不能调整审阅部成员或协调员。研发成员仍可直接给审阅成员发信，既不需要逐级转发，也不受职级高低限制。

### 在线编辑工具

管理员通过 `organization_edit` 提交 `{ reason, changes }`，一次 1–32 个动作，全部成功或全部回滚。工具采用成员完整姓名、部门完整路径和可用模型的可读名称；内部 ID、坐标、头像、对话绑定及 revision 不由模型填写。

| action              | 参数与效果                                                               |
| ------------------- | ------------------------------------------------------------------------ |
| `add_member`        | 必填 `name`、`task`；可选接收/交付说明、职级、管理身份、部门、模型和权限 |
| `update_member`     | 必填 `member` 与至少一个修改字段；原地修改，保留对话和邮箱               |
| `remove_member`     | 必填 `member`；立即撤销成员资格并终结该身份未完成邮件，保留对话与历史    |
| `add_department`    | 必填 `name`，可选上级完整路径 `parent`                                   |
| `update_department` | 必填 `department`，可修改 `name` 与 `parent`                             |
| `remove_department` | 必填 `department`；工具仅允许删除空部门，先移出直属成员和下级部门        |

省略字段保持原值；`department: null` / `parent: null` 表示直属组织。空字符串可清空接收说明或交付要求。默认新增成员职级 1、普通成员，继承调用者部门、本轮模型和实际权限所对应配置；新成员加入组织所选项目，创建本身不启动 Run。

修改模型或权限前，先查询 `organization_get_state` 的 `view=configuration`。在一次调用中合并同一对象的修改；新建成员或部门后先获取更新目录，再在后续调用中引用，不支持临时引用表达式。每次写入在事务中复核 Run、成员身份、实时目录、管理范围及 revision；冲突后重新查询并决定，不能凭旧快照重试扩权。

## 4. 邮件模型与六态生命周期

这里的邮件是应用内协作资料，不是外部电子邮箱。每次发送为每位收件人创建独立消息信封和输入收据，不跨消息组批。信封保存稳定 `messageId`、组织、发件/收件成员及当时绑定的对话名称、正文、时间和可选回复关联。发件身份来自可信 Host，模型不能填写或冒充。

| 邮件状态     | 含义                                      |
| ------------ | ----------------------------------------- |
| `pending`    | 尚未领取，仍在收件箱等待处理              |
| `processing` | 已被某个 Run 领取，等待正式投递或正在处理 |
| `processed`  | 已显式完成，或其正式所属 Turn 正常结束    |
| `stopped`    | 处理它的 Turn 被停止                      |
| `failed`     | 投递或处理 Turn 失败                      |
| `recalled`   | 发件人在尚未领取时撤回                    |

`processed` 只说明系统处理结束，不证明业务结果正确。输入收据的 pending/claimed/applied 是传输状态，不能替代邮件状态。历史失败不阻塞新信；已处理、已撤回邮件不被后续停止或失败改写。

### 发送与回复

`organization_send` 接受 `messages` 数组。新信使用准确成员名 `to`；回复使用收到邮件的 `replyTo`，由原信封确定原发件人。每封信只允许二选一；转交第三人使用 `to`。

```json
{
  "messages": [{ "to": "审阅员", "message": "请检查方案中的验收条件，将问题和依据发回给我。" }]
}
```

回复时使用实际收到的消息 ID，例如 `{ "messages": [{ "replyTo": "<收到的消息 ID>", "message": "已核对，发现两处条件缺失……" }] }`。发送成功只表示到达邮箱，不代表对方已开始或完成；不能靠普通最终回复或看板动画假定已交付。

邮件可以跨部门、跨职级交换。新任务、关键事实、阻塞和实质结果才需要发信；无新增任务、事实或问题的「收到」「待命」「验收通过」通常无需回复。明确要求确认、存在歧义或阻塞时可做一次必要回复，避免确认往返和占位邮件。

### 唤醒、领取与结算

1. 发送事务持久保存信封、输入与幂等回执，提交后通知调度器。
2. 普通空闲成员按到达顺序领取最早一封，经过现有根 Turn 准入后自动唤醒。
3. 系统正式交付本轮的邮件已经领取，直接处理，不再次调用 `organization_accept`。
4. 运行中其他来信留在邮箱，不自动插入。模型决定本轮处理额外 pending 邮件时，调用 `organization_accept({ messageIds })`；在同轮下一次安全采样边界正式投递，不新建 Run。
5. 正常结束时，本轮已正式接收且仍 processing 的邮件自动结算为 processed。只有要提前结算某封并继续其他工作时才调用 `organization_complete({ messageIds })`；它不会领取 pending 邮件。
6. 回到空闲仍有 pending 邮件时，再取最早一封启动下一轮；没有待办时保持空闲。

正式投递的模型信封包含原始 `Sent at`、实际领取时的 `Accepted at`（均为带 `Z` 时区的 UTC 时间），以及 `Delivery method`：自动唤醒为 `automatic wake-up`，本轮主动领取为 `accepted during current turn`。领取事务将这些信息固定在持久化正文中；实时投递、聊天投影和历史重放复用该正文，不以查询、重试或重放时间覆盖它。尚未领取的信封只标 pending，不生成领取时间。

审批等待、同步人工交互、运行中或并发名额不足均不视为可自动唤醒的空闲。模型、权限、配置或容量暂不可执行时由调度器退避重试，配置变更、容量释放及新信触发复查；调度器独立于前端页面。

用户手动停止会留下停止屏障，后续邮件保持排队，不立即唤醒。用户在该对话手动发送新消息后恢复正常机制；读取邮箱、组织查询或 World State 更新不会解除暂停。组织停用与用户停止是不同控制，二者都不能被模型查询绕过。

成员在本轮工作已完成或妥善交接、没有其他可推进工作且无 pending 邮件时正常结束；后续邮件会再唤醒，不必用 sleep、空转命令或循环查询维持 Turn。正常结束不等于整个协作任务完成，尚待回复的事项仍需如实说明。

### 查看邮箱与撤回

`organization_get_mailbox` 只读自己的 `inbox` 或 `outbox`。查询、预览和翻页不领取、不完成、不重发邮件。

- 收件箱中 `pending` 正文只是尚未接手的预览，条目的 `deliveryStatus` 为 `preview_only_not_accepted`。若要在本轮处理或回复，先调用 `organization_accept` 接手到本轮；否则原信仍保持 pending，之后可自动投递并唤醒新一轮。`organization_send` 回复不会自动领取或完成原信。
- 收件箱总览仅返回 pending/processing 正文；历史使用单独精简索引，不混入历史长正文。
- 待办及发件箱用 `nextCursor` → `cursor`；历史用 `history.nextCursor` → `historyCursor`，保持原过滤条件。
- `counts` 是整个所选邮箱的真实状态数量，不受本页和状态筛选影响；默认每页 20、最多 50 条。
- 指定 `direction` 和 `messageId` 精确读取一封正文及状态，仍严格复验邮箱归属。
- `organization_recall({ messageIds })` 只能撤回自己发出且仍 pending 的邮件；领取与撤回在事务内竞争，已领取不可撤回，撤回也不能抹去此前预览的内容。

发送、领取、完成、撤回和人员编辑以 Run + tool call ID 持久幂等。相同调用恢复原回执，不重新解析名称、不重复寄信或建人；同一调用 ID 携带不同请求会拒绝。收件身份在提交事务内复验，移除或重绑后同名成员不会误收旧授权发出的新信。

## 5. 查询、上下文与信任边界

普通成员挂载六个工具：`organization_send`、`organization_get_state`、`organization_get_mailbox`、`organization_accept`、`organization_complete`、`organization_recall`；管理员再挂载独立 `organization.management` 能力控制的 `organization_edit`。

仅已准入、当前资格有效且组织开启的独立根 Run 获得这些工具。下一次采样刷新能力，每次实际执行仍重新校验；历史、checkpoint、子 Agent 或分叉不能自授成员身份。组织 revision 与成员 incarnation 分离，其他成员变化不使本人 Run 自动失效，而本人移除/改绑后旧 Run 永不恢复该身份。

模型自动收到的 World State 仅含：

- `organization.execution`：组织名、公共背景和本人职责、部门路径、职级、管理身份及范围。
- `organization.mailbox`：本人 pending/processing 数量和上次实际观察后新信的简短提示。

每次采样由 Host 在同一个 SQLite 读取事务中取得当前有效身份和本人的邮箱摘要，只构建一次组织定义，不生成随后丢弃的其他成员运行状态。完整成员目录仍保留在可信身份中用于姓名寻址与权限校验；跨采样不缓存身份，关闭、移除或改绑后继续拒绝旧 Run 的权限。

全员目录、部门树和其他成员活动按需查询，不自动注入 `organization.awareness`。`organization_get_state` 要求简短用户可读 `reason`，提供五个视图：

| view            | 用途                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| `overview`      | 成员/部门数、状态统计、积压和有限关注事项                                                              |
| `structure`     | 部门树、完整路径，可限定部门与后代范围                                                                 |
| `members`       | 按姓名或职责关键词找成员；准确指定 `member` 可查完整职责                                               |
| `runtime`       | 实际活动、审批/交互等待、邮箱数量和最近 Turn 结果；准确指定成员并开启 `includeMail` 才附无正文邮件摘要 |
| `configuration` | 仅管理员查看本人和管理范围内成员的默认/下一轮配置及可执行模型                                          |

查询是带时间的实时快照，分页不冻结组织状态；默认 20、最多 50 条。成员邮件摘要独立使用 `mailCursor`。当前运行状态不能从上一次失败或处理中邮件数量推断；绑定不可用或缺少真实活动证据时明确返回 unknown。异步待回答问题不等于模型同步等待，下一轮草稿配置也不等于当前运行配置。

组织邮件是协作资料，不是用户本人指令、批准或新增权限。协作规则作为 `RequestOnly` 请求指令，不逐轮追加历史；实际邮件通过权威 `WorkflowDelivery` 进入上下文。主动领取回执供 UI 展示正文，但模型投影去除重复正文，正式投递只出现一次。UI 来信气泡不能当 HumanText 再次注入；分叉保留来源展示，但不继承组织资格或把这些展示副本重放成用户输入。

## 6. 看板、人工介入与恢复

组织首页、实例编辑和看板统一位于右侧栏。看板显示部门、成员活动与邮箱计数：悬停成员查看节点名称、职级、模型、权限与任务，单击不打开详情面板，双击打开实际对话；对话顶部组织菜单导航到其他成员，不区分上下游。邮件正文通过对话中的邮箱工具查看。

临时连线只来自已持久化的 sent/recalled 事件；撤回使用反向端点，领取和完成不伪造跨成员传输。首次打开、重开或隐藏期间不回放旧事件；事件按实例序号去重，动画不写入定义。收到、开始、结束和成功须以持久事实核对。

审批和人工交互沿用各成员对话的权限与交互入口。看板只展示稀疏 attention 状态，不自动批准、回答或恢复停止。组织连续运行时长来自真实已准入 Turn，重叠成员及明确委派的子 Agent 合并活动区间，不累加并行耗时；停用不会提前结束已运行 Turn 的计时。

启用时若成员模型不可用，提示按模型分组列出受影响成员，要求修复模型或调整组织配置；失败不修改启用状态与 revision。保存冲突保留草稿，提交成功但列表同步失败时重试同步，不重复创建实例。成员移除终结旧身份未完成邮件，保留对话；已提交回执恢复可读取原结果，但不授予任何新操作权限。

### Runtime 通知合并与恢复

`agent.workflows.runtime.changed` 发布元数据摘要：`inputs`、`inputRuns` 为空，保留事件窗口、暂停对话和新鲜偏好修改，并附带 `summary`。显式 `runtimeSnapshot` 默认仍返回完整投影；传入 `summaryOnly: true` 使用与通知相同的摘要读取。两种读取均保留真实事件序号，摘要不是完整输入或 Run 列表，不能凭空数组推断没有邮件或活动。

| 摘要字段              | 恢复语义                                                                                                             |
| --------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `pendingByNode`       | 当前成员绑定的真实 pending 邮件数，零值可省略；不从最近事件或有限输入窗口推算                                        |
| `conversationChanges` | 曾正式绑定 delivery 的每个对话及其最新关联邮件事件序号，包含已解绑成员和迟到的 Run 完成事件；不按最近 512 条事件截断 |
| `structureRevision`   | 最新 `members_changed` 事件序号，触发组织结构重新读取；没有结构事件时为 0                                            |

`summary` 的恢复事实与 `afterSequence` 无关。在同一个 SQLite 读取事务内取得实例事件水位、摘要和暂停状态，避免组合出跨版本快照。`events` 包含游标之后最新 512 条事件，再补充每个当前成员的模型、权限字段各自最新历史失效事件，按序号去重排序。因此历史偏好事件可能早于请求游标；消费者按字段去重并复核当前草稿，不能把它们当作新鲜偏好值，也不能重新播放动画。临时连线只使用新游标之后的真实 sent/recalled 事件。

对话变化水位由 `workflow_mail_conversation_changes` 在邮件写事务内维护，升级时从已有输入与事件回填。通知读取不再联表扫描全部历史输入和事件，也不读取邮件正文、输入 JSON 或 Turn Trace。结构与偏好通过索引定位最新事件。摘要大小会随曾接收邮件的对话身份数增长，并非固定长度；不会以静默截断丢失旧对话的恢复信号。此派生表只服务展示与恢复，不作为成员授权、投递资格或邮件处理完成的依据。

Core Server 按组织在第一次变更后开启固定 100 ms 窗口，窗口内后续变更只标记脏状态，不重新生成快照、不延后截止时间；单个 worker 串行读取投影，生成期间到达的变更保留到下一轮。持续活动不会因不断重置计时而饥饿，不同组织按各自截止时间刷新。此合并不改变邮件事务、投递调度、停止屏障或真实运行并发。

新鲜的模型/权限修改按成员、原 conversation 和字段合并，保留各字段最高的原始 organization revision；不能用另一个字段的较新 revision 抬高旧字段版本。一个 snapshot 可为同一成员携带两条不重叠字段更新，同 revision 可合一；每包仍限 128 个不同成员、256 条更新。窗口内成员重绑导致同 node 对应不同 conversation 时，保留原绑定，复用同一次投影分包通知。历史读取、启动恢复和回执重放不重新注入这些新鲜偏好，避免覆盖用户后来手动选择的草稿设置。

worker 由 bootstrap 显式启动并持有，构造服务不启动后台任务。暂时投影失败保留待发布字段，以指数退避重试、间隔最多 5 秒，新变更不能绕过退避；连续失败日志按指数次数收敛；权威查询确认实例已删除则终止该次发布，不把数据库暂时错误误当成删除。停止时先等待业务生产者和最终 Run/邮件结算，再在 outbound writer 关闭前预留 2 秒排空等待窗口，关闭阶段不重试；超时只读查询自然完成，已经开始的同步发送完成后关闭闸门，此后不能再发送或接受新变更。重启仍依赖持久数据重新读取 runtime，未成功送达的新鲜偏好不重放。可选性能诊断的 `workflow.runtime / projection` 记录实际投影次数与耗时，不逐事件打印。

## 7. 持久化与版本边界

当前 SQLite canonical schema 为 v71；definition schema v1、组织 revision 与成员 incarnation 是不同版本维度。

- v64 建立独立 `workflow_mail_*` 信封、输入、收发操作回执、事件、Run 身份、来源及停止屏障；不转换旧图执行记录。
- v65 将组织完整定义存入实例、解除对模板的外键依赖，保存独立成员身份及人员工具回执；精确 v64 升级不改写旧 Run 授权。
- v66 原子清除 7 张已退役 `workflow_execution_*` 图执行表及索引，保留当前组织邮件、人员回执和聊天。旧定义不会被自动转换或补齐，损坏/不兼容目录记录隔离展示。
- v67–v69 分离对话模型历史与展示版本，并避免未变消息的全文索引重写；不改变组织定义或邮件语义。
- v70 增加对话邮件变化水位派生表及结构、偏好事件索引，事务内回填既有历史并维护后续变化；原输入、事件和正文保留。

邮件终态结算与权威 Turn Trace 在同一事务提交，包括正常结束、停止、交互终止与启动恢复；没有正式投递证据的已领取邮件不能误标 processed。持久输入、Run/delivery 绑定和 Trace 共同防止重复投递。启动迁移和显式开发 reset 的支持范围不同，见[存储与数据生命周期](../architecture/storage-and-data-lifecycle.md)及[恢复 Runbook](../operations/recovery-runbook.md)。
