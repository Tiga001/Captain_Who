## 本次新确认的问题与修复

现有通知修复已把首次时间校验移到 writer FIFO 和 BEGIN IMMEDIATE 之后，并在事务末尾再次验证；但新 claim 的最后检查仍在 COMMIT 之前。若 COMMIT 本身耗尽 lease，会把已过期记录作为可投递 claim 返回。

本次在 `notification_repository.rs` 修复：

- 新 claim 在成功 COMMIT 后再次以同一新鲜时钟检查 expiry，过期时返回空集合。已提交事实保留，由正常 successor 流程回收，不伪造回滚或延长租约。
- 已有 claim 重放和 validate 的最终时间采样移到 ROLLBACK 返回之后。
- 继续保留晚到 ACK 的事实语义：同一 token 可记录已发生的投递；successor token 始终 fence 旧 ACK/release。

在 `service/notifications/tests.rs` 增加 `notification_claim_expiring_during_commit_does_not_return_delivery_authority`：commit_hook 将可控时间从 1000 推进到 6000，期限为 5000；断言记录确实已经提交但调用不返回投递权，后续 successor 正常拿到 attempt 2 与新期限。现有六个 lease/fencing 测试保留。

server `application/notification.rs` 在 repository 验证后还会读取 settings/items。这个额外等待可再次消耗期限，runtime_review 已补最终 DTO 返回前过滤，并保留单调时钟下限；另修复 prepared history stale source 丢失 history_version 后回退 admission 的 CAS 降级。server 侧运行结果以 runtime 交接记录和统一回归为准。

## FTS 强杀测试调查的复核

既有 `fts-crash-investigation/README.md.txt`、C/Python 最小复现和原始输出互相一致：在普通 UPDATE 之后（无需崩溃），曾执行 quick_check 的旧 reader 报 FTS checksum/index 异常；新 READ_ONLY handle 通过，旧 handle 经过普通 MATCH 后也通过。原调查在 SQLite 3.53.2 和 3.51.0 都观察到该现象。

这支持连接状态敏感的诊断异常，不支持已经确认内部缓存根因或新版 SQLite 回归的断言。本次把 `storage_faults.rs` 中确定性过强的注释改为上述实测边界；测试仍验证同一个原始隔离库，仍运行 quick_check/FK，未 rebuild FTS、改变 PRAGMA 或修理测试数据。新 handle 校验是合理的故障测试校正。

## 复核结论

- runtime checkpoint 身份/序号/fingerprint、终态退休及 ACK-loss 重放仍在原事务边界内；streaming SHA256 使用相同 serde JSON 元组，无内容/顺序省略。
- 新的 model-only history SQL 不读取历史展示/UI 字段；完整历史及展示 API 保持单独路径。cache key 区分 raw/model，两者共用原 count/byte 预算，最终 admission 保留历史版本与 metadata CAS。未修改这些 prepared-history 文件。
- commit hook 不是通知提交边界。update hook 只标记 dirty；连接释放前以 autocommit 和真实 journal head 推进发布 wake，失败/回滚不提前通知，失败核验保留 dirty。
- 单 writer、双 READ_ONLY/query_only reader、FULL、bounded FIFO/control reserve、reader/writer 关闭排空未被本轮更改。未完成事务在交还前回滚，失败隔离连接。
- terminal 仍在一个事务提交正文、Trace、模型上下文、usage、notification 和授权撤销；FULL 测试在末尾 notification insert trigger 注入，因此能覆盖已执行较早 SQL 的整体回滚。
- SQLite Backup API 测试在独立 reader 钉住旧 WAL snapshot 时验证最新完整 durable facts、pending action 与 notification cursor，并在恢复副本继续操作。只读 source backup 不保证恢复需要写原库的 hot DELETE journal；修正文档注释与实现一致。

## 未测与不可扩大结论

- SQLite max_page_count FULL 不等于主机文件系统 ENOSPC；未新增 VFS 注入，未验证真实 IOERR、fsync 错误、短写、磁盘拔除或断电。
- commit-hook-before / after-return 两个强杀边界不穷举 WAL 帧写入和同步期间每个失败点。
- backup 联合表等值不覆盖完整数据根中的外部附件、凭据后端、Provider continuation 文件及每一种 pending 外部动作；不能宣称完整产品恢复全部已测。
- notification lease 新鲜检查不会把跨进程 native delivery 变成绝对 exactly-once；不可把提交后返回值过滤描述成 IPC 到达后的无限期有效保证。
- 长稳态、公平性、积压、WAL 增长、生产 UI SLO 与物理累计写入量由父代理本轮实测决定；本代理不并行运行重负载干扰该测量。

## 额外只读审查：基准统计（修复权归父代理）

已读 `analyze.py`、`scripts/run-backend-concurrency-baseline.mjs`、其测试和完整 Rust baseline fixture。以下建议已发给父代理，未修改上述文件；状态仅代表审查时源码。

1. `analyze.py:49-56` 的 empirical pass 未纳入 runtime errors、unexpected errors、shutdown timeout、终态分布/控制注入完整性。即使 runner/Rust 已拒绝场景，单独分析该保留数据也可能得出 pass。建议将 runner integrity 结论纳入分析 checks，且仍展示全部失败样本。
2. `completed_turns_per_second` 用重开后 Completed 除以 cleanup 前 measured_us；未自然排空的场景会混入测量截止之后的结算。建议与 settled rate 一样在 drained=false 时为 null，或只计原窗口内终态，另列恢复后累计事实。
3. 名为 sustainability_checks 的检查只含最终排空和峰值，不验证积压趋势。应从 offered/responded 和 raw.terminal.at_us 重建业务未回执/未终态时间线，结合 queue count/bytes/oldest 分窗口趋势，或收窄名称与结论。
4. 对照同工作量应同时列 provider_requests、provider_request_bytes、output 体积、compaction events、根/子终态、每 owner 完成数。配置相同不自动等于实际有效工作相同；不同拒绝/取消分布会改变历史和后续准备量。
5. runner v2 仍在 `if (value?.raw?.rpcs)` 内做完整性检查；缺失整段 raw 可绕过检查。应对 v2 强制存在，并核对背景读取计划数 `floor(((waves-1)*interval_ms)/500)+1`。
6. queue count/bytes 表示该埋点持有的预约，部分包含执行中；不同 stage 不能相加当业务积压。所有窗口 peaks 合并方式正确，omitted 累加与 registry 每次 take 重置一致；omitted>0 应把观测视为下界，oldest 仍只是采样时点的最长等待。
7. proc_pid_rusage 的 I/O 是整个测试进程归属计数，包含 harness/假 provider；既不是 SQLite 专属，也不是设备/NAND 物理写入或 fsync 延迟。现源码注释正确，分析结果应保留 scope。RSS 含原本增长的持久历史和有限 raw records，不能直接据增长判泄漏或宣称恒定内存。
8. 普通发送与背景读取是固定提供时间表；approval/stop 在 pending/provider-first 就绪后反应式注入，延迟起点是 fixture 实际发起。对照可称同 cycle 和同根发送时刻，不应称所有控制操作在预先相同墙钟点发生。
