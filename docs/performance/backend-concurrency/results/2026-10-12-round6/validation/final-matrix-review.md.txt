## 当前 stage 直接定位

| 当前场景 | rpc.queue 聚合 | execution_permit_wait 聚合 /占 queue | write handler 平均 /p95 上界 | turn history_prepare /prepare_and_commit p95 上界 |

`bounded_dispatch.rs:530` write lane concurrency 明确为 2；`execute_job:344` 取得 fair execution permit 后持有至 handler 返回及回复入队。上述 execution permit 阶段 p95 上界为 short50 **720.895 ms**、long50 **1048.575 ms**，与最终尾延迟量级一致。short/long50 lane_wait 聚合只有2.050/2.295 ms，dependency_wait只有2.235/2.352 ms；owner resolution p95上界11.012/5.978 ms。故“写入执行名额等待占绝大多数 handler 前排队”是**当前实测定位**；不是旧 lane queue 队头阻塞，也没有证据说同 owner dependency 是这两组尾部主因。

同一 write handler 的平均服务时间从20短的24.1 ms增到50短30.6 ms、50长45.0 ms。50个近同时请求在两槽上排队会放大几十毫秒服务时间；简单均匀服务近似下，靠近第48个完成需要约24批，500ms对应每批约20.8ms服务预算。这只是定位用吞吐近似，真实服务分布/并发/入队顺序并不满足恒定服务，不能作为保证或据此更改业务额度。

`turn.rs:309` 的 admission_hold 是**每 Conversation** fence，不是全局锁；其总时长 short50 4558.164 ms、long50 6673.068 ms，接近各 handler_execution 4586.982/6745.634 ms。admission_wait 聚合只有0.130/0.175ms。不能把名为 admission_hold 的span误读成50 owner互相争抢同一个锁。真正下一步应进一步分解 handler 持有 execution permit 期间的业务工作和串行小storage调用。

writer/read是服务时间贡献候选，但当前证据未证明它们单独造成整段尾部：short/long50 writer queue_wait p95上界同为5.631ms，max14.122/21.774ms；read_wait p950.447/1.407ms，max3.689/10.553ms；writer hold p952.559ms（长50），turn_admission transaction p95短5.119/长6.655ms。很多小读写的总量与history prepare/commit会占用handler，不能把所有write permit排队都加到一个SQLite commit上。旧连接mutex等待此时几乎为零（short50全程0.109ms、long50 0.161ms），因为等待已显式迁到writer gate，单看sqlite.wait接近0也不能宣称storage无排队。

completion backlog仍值得跟进，但不应混成 durable admission 的直接阻塞：short/long50 completion queue_wait p95上界147.455/163.839ms，execution p95 36.863/53.247ms；60秒steady20 queue_wait p95为180.223ms。这些终态/投影/维护任务会和新发送共享storage与CPU，是否通过它们延长send handler需per-request关联或profile确认。prepare worker queue_wait p95短0.703/长3.071ms，相比write permit排队小，不能先称“两preparation workers饱和”。

当前timer lag p95短50 3.099ms、长50 2.894ms，max5.654/3.097ms；outbound.response queue p95上界24.575/32.767ms、max30.129/46.369ms，serialize p95仅10/7μs。因此此矩阵没有旧600秒baseline那种数百毫秒timer lag证据，优先改async runtime starvation/JSON wire encoding不能由当前数据支持。

## 代价与安全下一步

相同业务工作量下，总进程CPU **67.348→93.420秒（+38.71%）**、采样RSS峰值305086464→334626816 bytes、thread峰值26→48。text50短CPU +47.77%，长+23.85%，steady20 +67.07%；不能把当前延迟改善概括为CPU效率改善。增加了Core-owned耐久checkpoint等工作，进程还包含fake provider/harness；没有调用栈和per-feature CPU，不能据此定量归责给checkpoint。线程隔离是当前实现成本，不能再无证据增加lane或worker数“达标”。

1. 保留本次50短SLO失败，并等待600秒结果完成。后续profiling优先选短50/长50相同工作量，标记每个send handler在metadata/root access、history version/clone、model准备、writer准入/commit、resume/readiness/runtime handoff上的时间；现有两个粗span不足以确定剩余CPU函数。
2. 先减少两槽handler内重复small reads、同一不可变输入的重复clone/hash/assembly；只有确认同一个snapshot/版本内冗余后才消除。必须保留最终writer中的history/revision CAS、Preparing owner、execution access token、删除/关停围栏以及模型完整输入；账户license仍只约束新root准入。
3. 若profile指向checkpoint/terminal竞争，减少同一语义内的重复序列化/全量展示处理，仍保留exact sequence/fingerprint replay、terminal/pending flush及late terminal fence；不能减少模型正文、去掉终态耐久、合并不同owner或延长lease来换指标。
4. 任何后续代码变化先做定向correctness，再用独占A/B验证short50、long50与20mixed（含每owner进展和拒绝），同时报告CPU per accepted/provider request、logical/kernel I/O与payload bytes。提升吞吐、降低接纳量或稀释成功分位不能替代SLO达标。

本文结论只覆盖这个36场景finite matrix；没有新增负载、未证明长期无饿死/无内存增长，也没有把core scheduled intake当成完整界面操作延迟。
