## 本代理补充修复

### 通知 lease 不能在 response 组装等待后被当作有效交付权返回

`application/notification.rs` 的 storage claim/validate 返回后仍读取 settings 和 batch items。
reader 排队/SQL/DTO 组装可能耗尽 lease；原代码直接返回旧 claim DTO。现在入口建立 wall/Instant
下限时钟，所有数据读取完成后采新时间，以原 `claim_expires_at > completed_at` 过滤。
不新建事务、不延长 claim、不删除 durable claim，也不改变真实 native delivery 后旧 token ACK 的原收据语义。

新增 `application/notification/tests.rs` 三项测试：claim 响应期间过期、validate 响应期间过期、
截止前完整原样返回。使用临时磁盘/内存 credential backend 和确定性 response clock，隔离验证
storage 已发放有效 claim 后的最终响应边界，并断言过滤不改变 token/期限/attempt。
这是 Server 返回时的新鲜性检查；现有 DTO 不带 lease deadline，不能据此承诺任意 IPC 延迟之后仍有效。

### 陈旧 prepared history 不能降级并移除最终 model-history CAS

`agent_support/conversation.rs` 曾在传入 snapshot 的 `is_conversation_history_snapshot_current`
为 false 时将 `prepared_history` 置空，随后分开重读 trace/context，并让最终 append 的
`history_version` 变为 None。Trace-only 更新不会提升 conversation revision，因此这个 fallback
会丢失本来应保留的独立 model-history 围栏，也可能混用旧消息与新 trace/context。

现在这种陈旧输入直接返回既有 `Conversation changed after Turn preparation began; retry from
fresh history.` 错误；正常路径仍在最终 writer 事务验证完整 history version。新增测试仅更新旧
Trace `completed_at`，证明 conversation revision 不变但旧 source 不能接纳、不能插入新消息/Trace；
新的 coherent snapshot 可以接纳同一请求。

## 复用实现的静态审查结论

- `runtime_segment.rs` 已有 checked checkpoint begin 在 writer 获得连接之后和提交前检查精确
  Runtime generation、取消/关机、原 captured Wake token 与新鲜 lease；checkpoint 完成后再查 Wake。
  失效 token 不可给后继安装/覆盖 generation，不能通过读取当前 token 领用后继权力。
- checked begin callback 只短读 cancellation registry，guard 在后续 SQL 之前释放。复核未见该
  registry 跨 writer 等待的反向锁序；不将此结论外推到所有 registry。
- `RuntimeCheckpoint.pending` 从值变成 Arc，不改变序号、fingerprint、未确认精确重放及终态围栏。
- Preparing 仍是有界作业的 boot/generation owner，不另占或扩大逻辑额度。取消/删除保留 owner
  到实际退出；同 writer 最终准入验证、Project/Conversation scope 和全局未知 owner 回退保留。
- workflow 的运行期恢复仍只处理精确已终态 Run；claim→Trace 空窗由活跃 Preparing 保护，启动
  orphan reconciliation 与运行期 recover_run 没有混用。
- acceptance stdio 入口及凭据覆盖仅 `cfg(test)` 生效，要求 canonical temporary root 含
  `captain-acceptance-` 路径组件；普通生产 executable 没有此选择入口。

## 窄模型历史审查

SQL 只省略历史 `agent_run_json` 与 `chat_message_ui_states`，消息身份/角色/正文/时间/status、
folder refs、HumanInteraction投影、附件仍由原流程取得；Trace、model-context、有效 compaction
及 superseded-message 过滤仍来自同一 SQLite read transaction。模型组装函数只提取原有模型字段，
没有读取被省略的展示 JSON。Skill 选择/激活和新工具 schema 仍按本次 input、当前设置和冻结 workspace
生成，历史展示工具定义不作为运行授权或模型 schema 源。

`ConversationModelHistorySnapshot` 类型和 `to_append_record()` 明确用途；生产唯一转换调用是普通
append Turn 准备。函数入口拒绝把该 source 传给 rewrite/automation/continuation 等全保存路径。
最终 append 只写新消息，历史展示 JSON 不会被空字段覆盖。raw/full snapshot API 与 cache 分别以
model-only flag 索引，共享原有 entry/byte 上限；Renderer/full DTO 不会收到窄 cache 的条目。
prepared cache 仍是 32 entries / 128 MiB，未提高线程、队列或业务容量。

## 账户许可与 Wake lease 的不同契约

依据 `docs/subsystems/local-token-usage-and-license.md`：账户 license/本机 execution-access lease
只约束新的 root Turn 原子准入；退出或续租失败不取消已经准入的任务、审批、工具、子任务或自动化。
因此没有给已接纳 Runtime/checkpoint 加入账户许可复查。Wake execution lease 则是子任务持续的执行
能力，必须按 captured claim 在准备最终边界和终态写入验证。不能为了测试租约硬门槛而混淆两者。
