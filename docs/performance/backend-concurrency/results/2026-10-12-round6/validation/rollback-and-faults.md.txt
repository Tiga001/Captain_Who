## 回退候选、备份与操作边界

**本轮没有认证“最低可回退应用版本”，没有执行真实用户回滚，也没有用旧应用重开第六轮写入的副本完成端到端降级。** 可供下一次隔离演练选择的最近完整版本是第五轮 `6e7bd1cc`（实现提交 `e7237ce5`）：源码核对确认同为 v71、同 SQLite guard/WAL 及 Core checkpoint owner。它只是兼容性验证候选，不应写成已经验证的最早安全版本；回退还会失去第六轮通知租约及 prepared-history 修复。

有需要时的保守操作顺序是停止新生产者、正常关闭应用，等待已接纳写入及读取排空并完成 checkpoint/关闭，再保留升级前完整数据根与受支持 SQLite snapshot。在隔离位置用成套的目标 Host/Renderer/Core 验证副本的 schema、完整性、已确认正文、终态、pending/lease/cursor 与外部资源引用，然后决定发布。此处是待执行流程，本轮未对用户设备执行。不要在运行中的用户库切换 journal mode；旧 baseline 的 SQLite 3.46.0 不能直接视作当前多连接 WAL 的回退运行依赖。

`create_verified_sqlite_snapshot` 使用 SQLite Backup API 读取 source，不直接复制主 `.sqlite`：

1. source 以 READ_ONLY/NO_MUTEX/NOFOLLOW 打开；source/target 需通过普通文件与路径检查，target 必须是已有空文件。
2. 由 Backup API 纳入 SQLite 可读取的已提交 WAL 内容，分批复制；对 target 执行 `quick_check`，要求唯一结果 `ok`。
3. 关闭 source/target 的 SQLite handle，目标文件 `sync_all` 后返回。函数本身不负责原子发布 target，也不提供整个数据根或目录同步的统一恢复协议。

需要写 source 才能恢复的 hot DELETE rollback journal 会被只读 snapshot 路径拒绝；不能宣称此函数修复原库。相关注释已修正，本轮没有新增 hot DELETE 强杀演练。SQLite snapshot 不含附件/图片/Provider continuation 文件或操作系统凭据后端；跨设备复制数据库不等于复制这些依赖。`storage:reset-dev` 是显式丢弃运行历史、仅保留 allowlisted 配置的开发重建，不是回退/恢复命令。仓库没有受支持的一键完整 backup restore。当前 exact v71 配置来源与历史 reset allowlist 也不能由启动迁移支持集互相推断。

## 启动恢复的事实与限制

Agent 初始化按 startup reconciliation 处理孤立 Trace，并恢复 durable occupancy；显式 startup recovery 还恢复 workflow claims。合法 pending/suspension 保持原冻结身份与配置，未知外部结果保持保守失败/unknown，不能用当前 Provider、权限或盲重放付费请求补造进度。

server 回归组 37 的 `committed_stream_survives_process_kill_and_startup_reconciliation` 实际自启动子进程，在 runtime streaming checkpoint 已确认后杀死该子进程；新 StorageService 重开并显式调用生产 reconciliation，断言正文 `已保存 partial 🐈` 与 checkpoint sequence 保留、Run 收敛 `failed`。该测试不是启动完整打包 Electron 的用户恢复演练。该组共 **16 passed / 0 failed**，包含一个普通运行时空返回的 `process_crash_fixture` helper。

普通增量的 300ms 是 coalescing 调度窗口，不是磁盘堵塞下的持久化硬上限。崩溃保证限于最后已确认提交；Stop RPC 是取消请求接收，不是终态落盘确认。终态 Done 仍等待既有事务成功。迟到 generation/sequence/token 受原事务围栏约束；通知最终时间检查不保证跨进程原生显示与 ACK 的绝对 exactly-once。

## FTS 异常保留与测试校正

最初 `storage-faults.log` 为 **3 passed / 1 failed**：terminal before-commit 恢复后通过另一个连接重试终态，再在旧 pooled reader 第二次 quick_check 报 `fts5: checksum mismatch`。失败原日志保留，不能隐藏或改写为一直通过。

既有最小复现显示普通 UPDATE 即可触发相同旧-reader诊断，无需进程崩溃；fresh READ_ONLY handle 检查通过，旧 reader 普通 MATCH 返回正确内容后 quick_check 也通过。SQLite **3.53.2 与 3.51.0** 均有独立文本证据，后者报 malformed inverted index。原始 before/after-commit 隔离库的 fresh handle 检查均通过。这支持“连接状态敏感的完整性诊断”，内部缓存原因仍是工作假说；没有上游确认，也不能称只在新版引入的回归或普遍排除 FTS 缺陷。

故障断言现先释放 pooled reader，再对同一个原隔离库开 fresh READ_ONLY 做 quick_check/FK；未 rebuild FTS、修理数据或放宽 PRAGMA。最终新二进制 storage 全组已通过该测试。保留的 FTS README 当时写“待统一重编验证”是调查时间点记录，最新状态以上述最终日志为准；本次整理没有再次运行旧 C/Python 复现。

## 尚未覆盖与 I/O 口径

未做真实用户数据根迁移/回退、旧版本全套应用降级恢复、OS ENOSPC/IOERR/短写/fsync 错误/VFS 全点注入、断电、磁盘拔除或完整备份原子发布演练。`synchronous=FULL` 与 snapshot 的 `sync_all` 是代码中的请求/契约，不是完整硬件故障测量。

性能中的 `proc_pid_rusage` I/O 是整个测试进程归属计数，包含 harness/假 Provider，不是 SQLite 专属、物理设备/NAND 写入量或 fsync 耗时；不能据其累计值宣称证明完整持久化成本。WAL 字节、checkpoint busy/log/checkpointed 与长读 snapshot 进展需结合对应性能样本分别解释。性能最终门禁与数据留给统一验收，不由本稿代替。
