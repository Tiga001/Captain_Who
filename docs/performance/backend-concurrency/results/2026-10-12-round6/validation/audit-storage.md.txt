## 可操作发现与处理

### 1. 通知投递 lease 在 writer 排队后仍使用调用前时间（已写修复，待运行）

起点源码证据：

- crates/core-server/src/application/notification.rs:75、112 在调用存储前取 now_ms。
- crates/core/src/storage/service/notifications.rs:59-69、81-90 排入单 writer 后原样传入 caller now。
- crates/core/src/storage/notification_repository.rs:598/634 在 BEGIN IMMEDIATE 后仍以旧 now 创建到期时间；692/699 验证也使用旧 now。

复现：先取得 writer 并阻塞通知任务，任务按 T0 发起，推进可控时间跨过 lease_expires_at，释放 writer。旧实现仍按 T0 验证并返回可投递记录；新 claim 也可能刚返回便已经到期。这是投递有效性/重复提醒风险，不把它描述为模型或工具执行授权绕过。

当前修复：

- StorageService 的两个生产入口不再接受调用者 now；在入口建立 wall clock + monotonic elapsed 下限的时钟闭包，由仓库在真正取得 BEGIN IMMEDIATE 后调用。
- 新 claim 返回前再次核对时钟；若事务自身已耗尽整个 lease，回滚该事务并返回空集合，不能发布失效投递权。
- 已有 claim 的幂等返回及 validate 也在返回前重新核对 expiry；不通过重放隐式延租。
- 原 repository 固定时间 API 保留，转入相同实现的固定时钟分支，保持旧合成时间测试语义。
- 全仓调用检索发现两个 StorageService 生产调用者，均已更新；其余固定 now 调用属于 repository 测试。

当前定位：service/notifications.rs:20、61、98；notification_repository.rs:604、724；application/notification.rs:77、113。

新测试：crates/core/src/storage/service/notifications/tests.rs。

1. notification_claim_lease_starts_after_the_writer_barrier
2. notification_validate_rejects_a_lease_expired_behind_the_writer_barrier
3. notification_claim_expiring_in_its_transaction_rolls_back_the_claim

### 2. ACK/release 到期后仍可结算，不应机械增加 expiry WHERE（正确行为保留）

起点 notification_repository.rs:806、823 的 ACK UPDATE 和 release:852、872 检查 status + exact claim_token，没有 expiry 约束。

解释：validate 是开始投递前的有效性检查；ACK 是原生投递已发生后的事实回执。真实投递已经发生、但 ACK 因 writer 排队晚到时，如果仍是精确旧 token，应保存事实；若新 token 已接管，旧 ACK/release 必须被 fenced。此次不改变这层语义，新增上述第 5、6 项证明迟到回执保存及 successor fencing。该协议不能保证跨进程崩溃的原生 OS 提醒绝对 exactly-once，不作该承诺。

## Backup hot rollback 和回退边界

database_snapshot.rs 原 :10-11 声称“hot rollback journal 或 WAL 会被恢复并包含”。这对当前只读打开源的实现过宽：:19-21 使用 SQLITE_OPEN_READ_ONLY。当前 bundled libsqlite3-sys-0.38.2/sqlite3/sqlite3.c:64894 在 hot journal + readOnly 情况返回 SQLITE_READONLY_ROLLBACK。

已仅修函数注释：可读 WAL 提交由 SQLite 纳入；需要写源库才能恢复的 hot rollback journal 被拒绝，函数不负责修复原库。没有把唯一源改为读写，没有修改 backup 功能。

一个未来可安全补的拒绝边界回归：在 tempfile 自启动 DELETE-journal 进程，cache_spill 后未提交强杀；只读 Backup 应失败且源主库与 journal 字节不变，再复制“已停止的主库+hot journal”到另一个隔离身份验证 rollback 可恢复。主代理决定本轮不扩展热 DELETE 夹具以免拖延冻结，故未保留/运行该测试；不把它算通过。产品当前 WAL 业务 backup + process kill 是本轮实际补充目标。

回退必须先停业务生产者、排空已开始写入、checkpoint/关闭，再使用 SQLite Backup API 或已验证一致快照保留完整数据；不能只复制正在 WAL 运行的主 sqlite 文件。旧 SQLite 3.46.0 不可当作多连接 WAL 回退版本。任何模式切换不能在用户运行库实验。docs/operations/recovery-runbook.md:107 已明确仓库没有受支持的一键 backup restore；恢复 SQLite 也不等于恢复凭据/外部文件。
