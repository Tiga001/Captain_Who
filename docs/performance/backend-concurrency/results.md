## 三项最有证据的瓶颈

1. **普通写通道把独立对话的启动串行化。** `text-u50-r50-h0-s0` 的 150 个发送全部成功，计划投放至接纳回执 p95 为 **1002.674ms**，实际投放至回执为 1000.073ms。内部 `rpc.lane_wait/write` p95 桶上界 983.039ms，而 `rpc.handler_execution/write` 仅 36.863ms。长历史同格回执 p95 升至 **2235.920ms**，handler p95 桶上界 65.535ms。主要问题是多个短处理在同一队列累积，不能以增加队列长度代替拆除不必要的跨资源串行。
2. **独立审批通道仍继承无关启动的全局写入依赖。** `approvalbehindpreparation-u50-r50-h128-s0` 中，先让一个对话待批，再投放另外 49 个长历史启动，随后审批。唯一一次审批耗时 **2102.434ms**，其中内部 `rpc.dependency_wait/approval` 为 **2096.149ms**，真实 handler 仅 **3.847ms**。该受控交错证明全局屏障可以挡住审批，不是可靠 p95；后续必须按权威 owner 和资源因果关系迁移屏障，不能直接删除一致性保护。
3. **大子树启动时，承载执行路径的 Tokio runtime 出现明显调度停顿。** `tree-u50-r1-h0-s0` 根启动回执仅 7.995ms，但 78 个 20ms 定时探针的迟滞 p95 为 **631.319ms**、最大 **691.319ms**；同格 6,891 次 SQLite 连接获取累计等待 **3117.276ms**、累计持有 **1337.856ms**。双根 50 单元的最大迟滞仍为 427.771ms。源码中的同步子任务准备和共享存储是优先排查对象；现有探针尚不能给它们各自分配耗时百分比，也不能把累计锁等待说成 fsync 耗时。根 `turn.admission_*` 计数不覆盖所有子节点启动，后续需补子路径分段后再精确归因。

第三项的 timer 与基准内的真实 AgentService、TurnExecutor、dispatcher 共享 runtime，假模型在独立线程；不是正式 Electron 进程端到端测量。探针保持绝对 deadline，停顿后的追赶样本也计入分布。上述嵌套指标不能相加成总墙钟时间。

### 慢工具、稳态和资源

- 在 5 根场景中，一根实际执行 1/10/30 秒命令，其他 4 根审批均在该命令开始后、退出前投放；三个重叠校验均通过。审批最大耗时分别 **8.091/7.508/11.394ms**，没有随工具时长线性增长。这不能替代 50 单元混合压力测试。
- 20 根稳态按固定 2 秒间隔投放 31 批，**620/620 成功**，无拒绝/重试/未完成，全部恢复 Completed。测量约 60.6 秒，完成率 **10.231 Turn/s**；这是固定提供速率下的完成率，不是吞吐极限。回执 p50/p95/p99/max 为 **240.242/489.077/962.805/1331.879ms**，排队 p95 445.501ms。Provider 重叠峰值仅 5，不称为持续 20 路模型并行。
- 稳态每个 owner 均完成 31 次；owner p95 从 29.581 到 551.326ms，固定投放次序的尾部 owner 明显更慢。没有观察到饥饿，但整体 p95 不足以证明每个 owner 达标。
- 稳态累计 CPU 为 user 19.192s + system 3.239s；全部场景测量段合计 CPU 67.348s。这是 CPU 时间，不等于 wall time，也不是每个 Agent 的 CPU。
- 全运行 214 次外部采样：RSS 峰值 **290.953 MiB**、线程峰值 **26**，只含测试进程，不含工具子进程。rusage 的 291.188 MiB 是进程生命周期高水位，不拿相邻 case 的差值当内存增量。
- 稳态 write 队列峰值 19，结束 count/oldest 都为 0；所有场景正常清理后无遗留运行。最久排队应读逐请求 queue/max 或分派 histogram，不能把排空后的 oldest=0 写成没有等过。基准绕过 stdin 入站，未测该入口 pending-body 队列字节；生产探针已接入。出站队列峰值 **906,692 字节**；字节数为序列化负载，不是堆占用。
- 最大单格数据库文件 **40,280,064 字节**；当前 DELETE journal 下最终 WAL=0，不代表已经使用 WAL 或测过 checkpoint。macOS rusage 的 block I/O 读数为 0，实际设备写入字节 **unavailable**，不能推断没有磁盘写入。

## 测量边界

- Core Server 基准从计划/实际提交请求到真实分派器开始 handler、持久化接纳响应和本地模型首次收到请求；不含 Electron IPC、用户点击、React paint 或网络模型延迟。
- 本机 Apple M4、10 逻辑 CPU、16 GiB RAM；release、独立 target、debug info 0、incremental 0。完整版本、SHA-256 和参数保存在机器可读 metadata。
- 模型是独立单线程 loopback 服务，普通文本响应等待 50ms 后一次输出；停止场景保持流打开以测试真实取消，不是持续 token 流压测。工具使用临时目录中的安全 `printf` / `sleep`。1/10/30s 慢工具耗时与接纳/控制耗时分列。
- 单元数包括根与子 Agent，是场景人口，不表示它们在每一毫秒都同时运行；`provider_peak_connections` 给出观测到的模型请求重叠。
- 精确逐请求分位数与 Core Server 固定桶上界分开。小样本仍展示 p99 但不判为可信 SLO（夹具采用 n≥10,000 标识）；稳态固定提供负载不是吞吐极限测试。
- `rpc.pending_body` 是排队及正在执行的请求体，`rpc.queued` 到 handler 开始为止；bytes=0 的队列没有估算堆占用。`rpc.handler` 包含 blocking pool 等待，`rpc.handler_execution` 才是 handler 内执行。
- `turn.history_prepare` 包含历史读取及准备校验；`sqlite.committed/turn_admission` 当前计主提交路径，不覆盖既有 replay/permission-blocked 两个提前返回分支。
- 数据库文件/WAL/journal 字节是采样时文件大小；rusage block I/O 是操作数而非字节，不能据此断言实际设备写入量。RSS 高水位是进程整个生命周期，独立采样另给当前 RSS/线程数。
- reopen 是正常退出后重开，不冒充断电/崩溃恢复；ACK 丢失/回滚语义由独立回归覆盖。
- Renderer 与 Host 诊断接口已测试，但本轮不会自动对用户正在运行的真实桌面会话加压；前置 storage RPC 的逐个父子关联与 React paint 未测。
- release 基准开启仅用于测试的 `mycopilot-core/test-support`：允许本地假模型的 loopback HTTP，生产依赖图不启用；没有打开 debug assertions 或降低真实产品的 HTTPS 要求。
- 夹具会读取少量状态判断排空，诊断也有自身开销；本轮没有给出开关前后的 A/B 开销结论。后续性能对比应保持同样的探针和诊断配置。

## 验证命令与口径

构建采用：

```sh
CARGO_TARGET_DIR=/tmp/captain-backend-baseline-20261011-target CARGO_PROFILE_RELEASE_DEBUG=0 CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=4 cargo test --locked --release -p mycopilot-core -p mycopilot-core-server --lib --bin core-server --no-run
```

定向 Rust 回归覆盖诊断边界、通知与审批事务、Trace 回滚/ACK 丢失/跨连接变更/重开、占用、授权 epoch 和最终提交撤销、分派顺序及关停、基准原始载荷、模型 URL 约束。Host/Renderer 的 87 个 unit 与 15 个 browser 测试及 node/web 类型检查通过，命令见 [测量说明](host-renderer-measurement.md)。测试基础设施、文档链接和忽略测试归属检查另行执行。

严格 release Clippy 在本轮未改动的语句存在 3 处既有告警，不能报告全仓零告警：

- `crates/core/src/llm/stream.rs:950`：`collapsible_match`。
- `crates/core/src/storage/service/tests/run_attachment_files.rs:28`：`useless_conversion`。
- `crates/core-server/src/application/agent/turn_executor/launch.rs:15`：release 移除 debug 日志后产生 `unnecessary_lazy_evaluations`；该段原逻辑未改。

仅在检查命令中排除上述 3 类告警后，对两个变更 crate 的全部 targets 检查通过；没有修改项目 lint 配置：

```sh
CARGO_TARGET_DIR=/tmp/captain-backend-baseline-20261011-target CARGO_PROFILE_RELEASE_DEBUG=0 CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=4 cargo clippy --locked --release -p mycopilot-core -p mycopilot-core-server --all-targets -- -D warnings -A clippy::collapsible_match -A clippy::useless_conversion -A clippy::unnecessary_lazy_evaluations
```

初次搭建 release 夹具时，曾因默认凭据后端及 loopback HTTP 的开发模式限制失败。已通过显式测试凭据后端、dev-only test-support 修复，并重跑；失败启动不计入任何性能结果。首次正确冒烟在静态检查并行运行期间执行，只用作正确性验证，不作为延迟基线。

第一次完整矩阵也已判为无效：原测试模型的 128,000 上下文预算使长历史进入自动压缩，假模型不能提供有效压缩响应。最终夹具对所有场景统一设置 256,000，记录实际存储预算，要求无压缩事件和未知 Provider marker。此处固定的是合成模型配置，生产默认预算不改；长历史仍完整保留 128 对消息。这样只测准备/存储/分派，不把未实现的假模型压缩算作真实执行。该轮部分失败数据不用于任何性能比较。

第二次完整矩阵前 35 格通过，最后稳态的末批 20 个请求因既有测试授权 60 秒到期而正确拒绝，整轮仍判失败。最终夹具模拟正常 Host 续租：单次 TTL 仍不超过生产协议的 60 秒，每 20 秒通过真实 `set_execution_access` 递增 revision、保持 identity epoch 续租，总寿命有界且退出时停止任务。记录每次续租时刻和实际期限，不绕过权限校验、不缩短 31 批负载，也不把授权拒绝算作容量拒绝。此轮数据同样不用于最终比较。
